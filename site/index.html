Say what your program is for. One file, one build, one native executable.

A compiled, intent-oriented language for fast, resource-efficient software development by humans and AI agents. One typed file holds the program, its components, its contracts and its policies; the compiler turns it into native executables, then runs and checks them.

package examples.terminal

import std.console.CommandConsole
import std.protocol.telnet.{TelnetServer, TelnetClient}

system Terminal {
  resource ingress: TcpListener {
    address = "127.0.0.1"
    port = 2323
  }

  component console: CommandConsole {
    implementation = module("examples.terminal.commands")
    prompt = "terminal> "
    maximum_line = 4096 bytes
    command_schema = module("examples.terminal.command_schema")
  }

  component server: TelnetServer {
    listener = ingress
    application = console
    executable = "terminald"
  }

  component client: TelnetClient {
    target = ingress
    executable = "tn"
  }
}
import std.console.{Reply, Action, first_word, rest_after_word}

enum Command {
  Help,
  Echo(Text),
  Status,
  Quit
}

fn answer(command: Command) -> Reply = match command {
  Help => Reply { lines = ["help", "echo <text>", "status", "quit"] }
  Echo(text) => Reply { lines = [text] }
  Status => Reply { lines = ["ready"] }
  Quit => Reply { lines = ["bye"], action = Close }
}

fn parse(line: Text) -> Option<Command> = match first_word(line) {
  "help" => Some(Help)
  "status" => Some(Status)
  "quit" => Some(Quit)
  "echo" => Some(Echo(rest_after_word(line)))
  _ => None
}

test "parse reads the four commands by their first word" {
  assert parse("echo hello world") == Some(Echo("hello world"))
  assert parse("quit now") == Some(Quit)
  assert parse("HELP") == None
}

Build speed

Built for many agents compiling at once

Ignite exists in part as a replacement for Rust, because rustc takes a long time to compile. In agentic software development many agents work at the same time and each of them runs compilations; with rustc, that grinds the machine to a halt. Compilation caches did not solve it.

In Ignite a whole program can be one file. It compiles in one step, and on the LLVM target clang compiles and links the result: no cargo, no crate graph, and the binary is there. The todo HTTP service builds in 0.22 s (dev) and 0.75 s (release) on the LLVM target. LLVM is the default target; the Rust target, built by cargo, takes 2.5 to 3.2 s for the same program and stays as the differential check (--target rust).

For many agents the figure that adds up is CPU time, not wall time: N builds at once need about N times the CPU seconds of one. Eight LLVM-target builds of the todo service started together finished in 0.34 s and used 2.4 CPU seconds between them.

Planned, not built

Specified, then checked

Ignite is meant as a native realization target for ESS, which turns intent into typed, machine-checkable specifications with conformance suites. ESS stays language-independent: the conformance tests it generates check an Ignite executable like any other. None of this is built yet; the plan is in the ecosystem review.

One toolchain, source to operations

From one program to a running, supervised system

  1. checkParse and check the program and the standard library. No output on success.
  2. testBuild the inline tests and run them, on Rust, LLVM or both.
  3. buildGenerated Rust built by cargo, or LLVM IR compiled and linked by clang.
  4. planPrint the system model as canonical, deterministic JSON.
  5. explainExplain one system, member, property or assembly, with its source line.
  6. runBuild the members, start them, probe them and evaluate the contracts.
  7. replayRe-step the journal and compare every effect and standing.
  8. applyApply a saved, source-bound plan through a local host, with durable receipts.

Why Ignite

Intent that the compiler can hold you to

System intent is usually split across application code, infrastructure definitions, deployment configuration, monitoring queries and runbooks, and those can disagree. Ignite keeps it in one typed model.

Intent first

Sizes, durations and ratios are typed quantities: 4096 bytes, 15 minutes, 99.9%. Contracts, restart policies and deployments are declarations the compiler checks, not comments next to a YAML file.

Intent and properties

Protocols are code

Telnet and HTTP are written in Ignite, in the standard library, generic over any byte stream. Their session tests run in-process over a pipe. Nothing application-specific hides in the runtime.

Protocols and roles

One substrate, two targets

LLVM, the default, built and linked with clang, and Rust, built with cargo. Both call the same IO substrate and behave the same, down to the text of an error.

One substrate, two targets

Effects are explicit

A function names the capabilities it uses with requires [...]. Property expressions are pure and evaluated at compile time under a fuel limit, so configuration cannot reach the network.

Effects and capabilities

Operate what you declared

ignite run supervises the members, runs the probes, evaluates the contracts and journals every event. ignite replay re-derives the same effects and standings from that journal.

Plan, explain, run and replay

Tests live next to the code

A test block sits beside the function it checks. ignite test --target all links one test executable per target and runs every test on both.

Testing with ignite test

Contracts and policies are declarations

An objective with a measurement behind it

The full terminal declaration adds a probe, three contracts, a restart policy and a drain rollout. The compiler evaluates every property, and ignite explain shows what a declaration means, where it came from and which machine will enforce it.

  • Missing telemetry is insufficient evidence by default, not a success; a contract that wants otherwise says counts_as_good or counts_as_bad.
  • A contract is bound to the signal it observes, checked before anything runs.
  • The machines are pure reducers in std.control, stepped by ignite run.

  interval = 10 seconds
  timeout = 2 seconds

Failure is contained

A failure ends its task, not your server

A failed assert, an integer overflow or an out-of-range index stops the one session that hit it and reports the file, line and column. Every other session carries on.

Quickstart

From a clone to your first Ignite system

You need git and Rust (stable, with cargo). The Rust target builds programs with cargo; the LLVM target needs clang. Ignite installs from source.

  1. Install the compiler from a clone

    git clone https://github.com/ignite-lang/ignite
cd ignite
cargo install --locked --path crates/ignite

    This puts ignite on your PATH. Keep the clone: ignite reads the standard library from it.

  2. Compile the terminal system

    ignite build examples/terminal/terminal.ignite

    This builds terminald and tn into target/ignite/terminal/target/debug/.

  3. Start the server, then connect

    target/ignite/terminal/target/debug/terminald    # terminal 1
target/ignite/terminal/target/debug/tn           # terminal 2

    Type help, echo hello, status and quit. Any Telnet client works too: telnet 127.0.0.1 2323.

  4. Run the example's tests

    ignite test examples/terminal/commands.ignite

    Four inline tests, among them the whole Telnet session over an in-process pipe.

  5. Look at the system as the compiler sees it

    ignite plan examples/terminal/terminal.design.ignite
ignite explain examples/terminal/terminal.design.ignite local

Where it stands

Early, honest, moving

Ignite is an early prototype. The language, both native targets, the standard library, the system declaration, planning, running, journal replay, local apply and protocol conformance claims work today. The syntax is not frozen and the design is versioned.
