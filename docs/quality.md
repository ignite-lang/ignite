# Quality metrics

The written set of Ignite's quality metrics (story `quality-ratchet`, 2026-11-07). The first
assessment, run on the merge of that story, is the bar: no merge makes a gated metric worse, no
release is worse than the release before it, and an improvement is written into the bar in the
change that makes it, so the bar moves one way only. The book's page `site/book/src/quality.md`
shows the same metrics with their current values and trend.

## Files

| file | holds | written by |
|---|---|---|
| `quality/baseline.json` | every metric: area, kind, direction, tolerance, instrument, source, target where set, the bar per target, the decisions that moved a bar (`decision`) or loosened a tolerance (`tolerance_decision`); `known_differences`, `intermittent_decisions`, `eval_cannot_run` and `eval_slow` of the differential runner | by hand for a new metric or a decision; `IGNITE_BLESS=1` for an improvement or a new value |
| `quality/history.jsonl` | one record per metric, target and run: `commit`, `date`, `host` (`local` for this workstation, `ec2:<type>` for the dedicated timing host), `run` (`bar`, `vX.Y.Z` or `run`), `metric`, `target`, `value`, and the 1-minute `load` for a timed row on `local`; a dedicated-host record also has `machine`, `base` and `base_value` (below) | `task quality` (`quality::record`; `IGNITE_QUALITY_HOST` sets `host`, default `local`); the dedicated-host records `task quality-remote` |
| `quality/bench.jsonl` | the native benchmark's absolute values, one record per run, program, cell and implementation: `commit`, `base`, `date`, `host`, `run`, `program`, `cell`, `implementation` (`head-llvm`, `head-rust`, `base-llvm`, `base-rust`, `native-rust`, `native-go`), the medians `rps`, `p50_us`, `p99_us`, `peak_rss_kib`, the stripped `size_bytes`, `errors` and `passes` | `task quality-remote` |
| `quality/trend.md` | one row per release (and the bar) with the change against the row before; timing rows on `local` counted apart as not comparable; a second table with one row per dedicated-host run (timing rows), a third with one row per run and benchmark cell (ratios against plain Rust) | generated from the history by `task quality` and `task quality-remote` |
| `site/book/src/quality.md` | the book page: every metric per area and target, its bar, current value and trend | generated by `task quality`; `site::quality_page_is_generated` checks it |

## Kinds, targets and sources

- **gate**: a count of failures or violations; the bar is never above today, usually 0.
- **ratchet**: a value with a direction (`lower` or `higher` is better) and a tolerance, a count
  or a percentage of the bar.
- **hill-climb**: tracked and aimed at the target the table names; its bar stays the first
  assessment's value, and a merge records a move either way, not refused (a missing value is).
  A release judges it like any other row: worse than the last release is refused (section
  "`task quality` and releases"). Once the target is reached the metric becomes a gate.

A metric that differs by target has one bar per target: `rust` (the Rust target), `llvm` (the
LLVM target) and `eval` (the compile-time evaluator, where it runs); `all` is a value that does
not differ by target. A bar's key may add a part after a `/`, as `rust/patterns` or
`llvm/todod/release`.

Each measured metric has one source:

| source | measured by | when |
|---|---|---|
| `differential` | `differential::corpus_agrees_across_rust_llvm_and_the_evaluator` (`crates/ignite/tests/differential.rs`) | every merge (`task gate`) and `task quality` |
| `static` | `quality::static_metrics_hold_the_bar` (`crates/ignite/tests/quality.rs`) | every merge and `task quality` |
| `conformance` | `quality::conformance_claims_hold_the_bar` | every merge and `task quality` |
| `perf` | `ignite-perf quality` (`tools/ignite-perf/src/quality.rs`), each value with the 1-minute load at its start | `task quality` only. The sizes (3.2, bytes) are deterministic and held against their bars like any count. The timing rows (ms: 5.3, 6.1, 6.2, a fixed list in `quality::TIMING`, not read from the labels) are recorded as `host: local` and gate nothing, because timing on the shared workstation is not comparable between runs. Their bars are the first assessment's local values, kept as a reference. `task quality-remote` measures these rows on a single-tenant EC2 host (`host: ec2:<type>`, section "The dedicated timing host"); a release is refused there on a timing row worse than the last release. |
| `bench` | the native benchmark of `ignite-perf quality-remote` (`tools/ignite-perf/src/bench.rs`, section "Against plain Rust") | `task quality-remote` only. The rows 3.3, 3.7, 3.8 and 3.9 (a fixed list in `quality::BENCH`), ratios in permille. `quality::trend_and_docs_are_generated_from_quality` refuses a target of the latest run without a bar and an improvement not written into the bar; a release is refused in the run on a ratio worse than BASE's. |

The per-merge tests refuse, as the UI ratchet (`ux/baseline.json`, `site::ux::ratchet`) does: a
value worse than its bar beyond the tolerance, a bar the run did not measure, a measured value
without a bar, an improvement not written into the baseline, and, against `main`'s baseline, a
bar made worse without a `decision` of its own (present and, trimmed, none of the decisions `main`
holds anywhere in its baseline), a tolerance loosened without a `tolerance_decision` of its own, and a metric whose
source, unit or direction changed (a different measure is a new metric id).

## The differential runner

Metric 1.1 is the gate `story:mid-level-ir` lands behind. The runner takes every `.ignite` file
with inline tests or an executable under `crates/ignite/tests/fixtures/` (diagnostic fixtures,
those with an `.expected` file, left out), `examples/` (design files left out) and `std/`, that
checks. Each inline test runs as the test runner runs it (`--run-one`) on both targets, in the
executable built for its file (two files with one module path, as every file without a `module`
line is `main`, get two executables), and through `Evaluator::run_test`; each executable runs without arguments on both targets, except a server
or a process starter (a system with a `TcpListener` or a `Launcher`), and the evaluator runs a
printer's main (a component of type `Printer`: the debug text of every fn without parameters).
Rust is the reference: LLVM agrees when exit status, stdout and stderr are equal, the evaluator
when it passes where Rust exits 0 or fails with the report Rust prints where Rust exits 101.

Every unit has a run on Rust and on LLVM, or a listed reason (a main a `not run:` line names); a
unit without either fails the gate. The Rust builds start from the workspace's `Cargo.lock` (copied
over each generated project's lock before every build) and run `cargo --offline`, so they resolve
from the lock and the local cargo cache and never touch the network. A test the executable does
not hold (exit 2, `no test named …`) is no run.

A difference fails the gate unless `known_differences` lists it with its consumer and the story
that fixes it (and a failing test committed `#[ignore = "story:<id>: …"]`); a listed difference
that is gone fails too. A difference that depends on the machine's load (a timing assertion) is
listed with `"intermittent": true` and names an open story (draft, proposed or active) of `.engineering/planning/story/`;
a unit `main` does not list as intermittent needs an `intermittent_decisions` entry of its own: it may show
or not in a run, is not refused as gone and is not counted in 1.1, which counts the steady
differences. The number of intermittent entries is the gate 1.7, which may only go down. The
units the evaluator cannot run are listed in `eval_cannot_run` with the reason, compared exactly;
their count is metric 1.6. A unit listed as over the evaluator's time limit is not evaluated in a
merge run (only by `task quality`), so it also needs an entry in `eval_slow` with the decision that
listed it, one `main` does not already hold for it. Every outcome of a run is in
`target/quality/differential.json`.

## `task quality` and releases

`task quality` measures every instrumented metric once: the three per-merge tests, then
`ignite-perf quality`, then `quality::record`, which appends the run to `quality/history.jsonl`
with its host and regenerates `quality/trend.md`, the table below and the book page.
`IGNITE_BLESS=1 task quality` writes improvements of the count rows into the bars and gives a
timing row without a bar its first value. With `RUN=vX.Y.Z` the run is a release:
`quality::record` refuses it when a row is worse than at the last release by any amount, and
then records the run as `run`, not as the release. The last release is the one that was
published: the newest `v*` tag reachable from HEAD other than the candidate, and its values are
the history's last local run under that label; records under any other `v*` label (a candidate
the gate refused, the candidate itself) are never the reference, a tag without a record in the
history refuses the release, and so does a history with a `v*` run whose tag cannot be read
(no tags fetched, a shallow clone, git failing: the refusal says so and names
`git fetch --tags`); the `bar` run is the reference only when the history holds no `v*` run. Every
row it judges is a deterministic value (a count, or a size such as 3.2), so its tolerance there
is 0, whatever the metric's tolerance for a merge; a hill-climb row is judged like any other.
No `decision` holds a row for a release (no release is worse than the release before it on any
row, `AGENTS.md` § Releases): a merge may still move a bar worse with a `decision`, but a bar a
decision moved worse than the last release refuses the release, whatever the measured value,
until the decision is withdrawn, and the refusal names the decision. Timing and benchmark
rows are not part of that refusal: they are judged only on the dedicated host's records, where
`task quality-remote` refuses them (next section). The release steps in `AGENTS.md` § Releases
run both.

## The dedicated timing host

Timing on the shared workstation is not comparable between runs, so the timing rows (5.3, 6.1,
6.2) that count are measured on a machine that runs nothing else:
`task quality-remote BASE=<rev> HEAD=<rev> [RUN=vX.Y.Z]` (`ignite-perf quality-remote`,
`tools/ignite-perf/src/remote.rs`).

- **Host.** One EC2 `c7i.metal-24xl` (a whole host: 96 vCPU, 192 GiB), spot in the zone with
  the lowest spot price, on-demand only when no zone has spot capacity (`INSTANCE_TYPE` changes
  the type). Ubuntu 24.04, clang from apt.llvm.org, Rust stable; the user-data stops the
  periodic services and turns SMT and turbo off and the governor to `performance` where the
  instance allows it. What the host actually reports (CPU model, kernel, SMT, turbo,
  governors, clang and rustc) is recorded, not assumed.
- **Access and account.** The aws CLI with the profile `IGNITE_PERF_AWS_PROFILE` (required, no
  default) and the region `IGNITE_PERF_AWS_REGION`. A security group admitting SSH from the
  operator's address only and an ed25519 key pair are made for the run; every resource carries
  the tag `ignite-quality-run=<run id>`.
- **Bounds.** One instance per run. It terminates itself after `MAX_HOURS` (default 3: a
  `shutdown -h` timer with instance-initiated shutdown set to terminate). The mode terminates it
  and deletes the group and key pair on every exit path (success, failure, SIGINT, SIGTERM,
  SIGHUP), then lists by the run tag and fails when an instance, group or key pair is left.
  `DRY_RUN=1` makes the read-only calls and every creating call with EC2's `--dry-run`;
  `remote::` in `tools/ignite-perf/tests/` checks that plan, the spot-then-on-demand order and
  the cleanup after a failure without AWS, in `task gate`.
- **Method.** The trees of BASE and HEAD (`git archive`) and of the commit running the mode, the
  harness, are copied to the host; both compilers and runtimes are built there. The harness's
  `ignite-perf quality --timing-only` runs over each tree: one discarded warm-up of HEAD, then 5
  passes interleaved ABBA (base, head; head, base; base, head; …), each pass the medians of 15
  check and plan runs and 3 todo builds per target and one real-clock restart. A row's value is
  the median of its passes.
- **Records.** One record per timing row: HEAD's median as `value`, `host: ec2:<type>`, `base`
  and `base_value` (BASE's median from the same run), the median `load` on the host, and
  `machine`: instance type, CPU model, kernel, `smt`, `turbo`, governor, clang, rustc, market,
  `usd_per_hour`, `instance_hours` (launch to terminated, the mode's own clock) and `cost_usd`.
  No instance id, account or zone is recorded. `quality/trend.md` lists these runs in their own
  table, compared only with runs on the same host type, and the book page shows a timing row's
  latest value from them.
- **Releases.** With `RUN=vX.Y.Z` and BASE the last release tag, a row refuses the release when
  HEAD's median is worse than BASE's beyond the metric's tolerance (`quality/baseline.json`),
  and also when HEAD's median is worse and every HEAD sample (pass) is worse than every BASE
  sample, by any amount (a row of one sample each: any worse value). The tolerance is only a
  bound on noise: where the samples overlap the difference is not shown and the tolerance
  decides; where they do not, the row is worse. With 5 passes two equal builds have disjoint
  samples on one row by chance in 1 of 252 runs (1 of 20 with 3). A run judges 41 noisy rows (5
  timing rows, 36 llvm and rust benchmark rows), so if the rows are independent two equal
  builds are refused by this rule in about 15 % of runs. A release run refused only by this
  rule, on rows inside their tolerance, is run once more; a row refused in both runs stands. A
  release run takes at least 5 passes (`--passes`, `--bench-passes`; fewer is an error before
  anything starts). No `decision` holds a row. A refused run's records are labelled `run`, and
  the mode exits 1. Both trees are measured on the same host in the same run, so the refusal
  does not compare across machines.
- **Cost.** The first run (BASE = HEAD, an A/A run) took 0.23 instance-hours from launch to
  terminated, 0.23 USD at the spot price, of which about 7 minutes were the termination; its
  passes agreed within 0.3 %. Each record carries its run's cost (`machine`).

## Against plain Rust

The same run measures the two example programs against hand-written implementations of the same
behaviour (`bench/native/`, rows 3.3, 3.7, 3.8 and 3.9), after the timing rows
(`ignite-perf quality-host --no-bench` leaves it out).

- **References.** `bench/native/rust/` is its own Cargo workspace with its own lockfile, excluded
  from the main one; `bench/native/go/` uses the Go standard library only. Each is written the way
  a competent programmer would write the program, not tuned beyond it:
  - todo, plain Rust: hyper 1 (HTTP/1.1) on tokio's multi-threaded runtime, the store a `BTreeMap`
    behind a mutex, a hand-written strict JSON reader; Go: `net/http` and `encoding/json`. Both
    answer the same routes with the same status codes, bodies and `Content-Type`s as todod and
    write every change as `todo-data/<shard>/<id>/<version>.json` (a temporary file renamed into
    place, older versions removed, no `fsync`, as todod). They load the directory at start;
    todod loads it on the first request. Their other response headers are their library's.
  - terminal, plain Rust: one OS thread per running session, a finished thread kept for up to
    1 s and handed the next connection, as `ignite-io`'s task threads are
    (`bench/native/rust/terminal/src/workers.rs`), so the `connect` cell measures the protocol
    and not thread creation; Go: one goroutine per connection, which the Go runtime schedules
    on reused threads already. Both decode Telnet as `std.protocol.telnet` does (CR LF, CR NUL, a lone CR or LF
    ending a line, `DO` refused with `WONT`, `WILL` with `DONT`, AYT, IP, `IAC GA` after every
    prompt, the line and subnegotiation limits, the idle timeout) and answer the console's
    commands with its texts. They do not implement the Synch (urgent data), which no cell sends.
- **Same behaviour first.** Before any timing, `ignite-load check` runs one functional check per
  program against every binary (the todo routes of the example's inline tests in order, the
  terminal's transcript); a binary that fails it fails the run.
- **Cells.** terminal: `rr` with 1 and 64 connections, `connect` with 8; todo: `GET /todos/1` with
  1 and 64 connections and `PATCH /todos/1` with 16, against one seeded todo
  (`ignite-perf::bench::CELLS`). Each cell runs 5 s after a 1 s warm-up.
- **Implementations.** Ignite on the LLVM target and on the Rust target, each built from BASE and
  from HEAD (`--release`), plain Rust, Go: six servers per cell.
- **Machine.** Loopback; the server pinned to CPUs 2 to 5, the load generator to 8 to 31
  (`sched_setaffinity`, `--server-cpus`, `--load-cpus`), so neither competes with the other or
  with CPUs 0 and 1. Each server starts in a fresh working directory.
- **Passes.** 5 passes (`--bench-passes`; the timing rows take 5 too, `--passes`), the servers of a cell in one order in odd passes and reversed in even ones
  (ABBA). Every ratio is taken within a pass, an implementation's value over plain Rust's in the
  same pass, and a row's value is the median of the pass ratios; a run with errors is left out,
  and a cell without a plain-Rust value fails the run.
- **Rows.** 3.3 replies per second (higher is better), 3.7 p99 latency, 3.8 the server's peak RSS,
  3.9 the stripped release binary (lower is better), each in permille of plain Rust. Targets are
  `llvm/<program>/<cell>` and `rust/<program>/<cell>` (`llvm/<program>` for the size); `go/…` is
  recorded as the reference and has no bar. The bars are the first run's ratios; a later run's
  improvement is written into them (`IGNITE_BLESS=1`).
- **Releases.** With `RUN=vX.Y.Z` a row whose HEAD ratio is worse than BASE's in the same run beyond
  the metric's tolerance (3.3 10 %, 3.7 20 %, 3.8 10 %, 3.9 5 %), or worse in every pass than
  every pass of BASE, refuses the release, as a timing row does.
- **First run.** BASE = HEAD (an A/A run, 2026-11-08, 5 benchmark passes), 0.65 instance-hours on
  spot, 0.63 USD, timing rows and benchmark together; its ratios are the bars (`quality/trend.md`,
  "Against plain Rust"). Within the run BASE and HEAD agreed within 1.7 % on every throughput, RSS
  and size row and within 3.0 % on every p99 row (`rust/terminal/rr-64`), so 3.7 keeps its 20 %
  tolerance. An earlier run over 3 passes, with a plain-Rust terminal that started a thread per
  connection, was replaced; one p99 row differed 17.9 % there.

## Hill-climbing

The `target` column names the target of a metric where one is set. A wave that moves a metric
records the change in its close (the wave page under `.engineering/waves/` and the PR body): the
metric, the target, the value before and after, and the run of `task quality` that measured it.
A merge may move a hill-climb row either way; a release may not move it worse than the last
release.
