# Quality metrics

The written set of Ignite's quality metrics (story `quality-ratchet`, 2026-11-07). The first
assessment, run on the merge of that story, is the bar: no merge makes a gated metric worse, no
release is worse than the release before it, and an improvement is written into the bar in the
change that makes it, so the bar moves one way only. The book's page `site/book/src/quality.md`
shows the same metrics with their current values and trend.

## Files

| file | holds | written by |
|---|---|---|
| `quality/baseline.json` | every metric: area, kind, direction, tolerance, instrument, source, target where set, the bar per target; `known_differences` and `eval_cannot_run` of the differential runner | by hand for a new metric or a decision; `IGNITE_BLESS=1` for an improvement or a new value |
| `quality/history.jsonl` | one record per metric, target and run: `commit`, `date`, `host` (`local` for this workstation, `ec2:<type>` for the dedicated timing host), `run` (`bar`, `vX.Y.Z` or `run`), `metric`, `target`, `value`, and the 1-minute `load` for a timed row on `local` | `task quality` (`quality::record`; `IGNITE_QUALITY_HOST` sets `host`, default `local`) |
| `quality/trend.md` | one row per release (and the bar) with the change against the row before; timing rows on `local` counted apart as not comparable | generated from the history by `task quality` |
| `site/book/src/quality.md` | the book page: every metric per area and target, its bar, current value and trend | generated by `task quality`; `site::quality_page_is_generated` checks it |

## Kinds, targets and sources

- **gate**: a count of failures or violations; the bar is never above today, usually 0.
- **ratchet**: a value with a direction (`lower` or `higher` is better) and a tolerance, a count
  or a percentage of the bar.
- **hill-climb**: tracked and aimed at the target the table names; its bar stays the first
  assessment's value, and a move either way is recorded, not refused (a missing value is). Once
  the target is reached the metric becomes a gate.

A metric that differs by target has one bar per target: `rust` (the Rust target), `llvm` (the
LLVM target) and `eval` (the compile-time evaluator, where it runs); `all` is a value that does
not differ by target. A bar's key may add a part after a `/`, as `rust/patterns` or
`llvm/todod/release`.

Each measured metric has one source:

| source | measured by | when |
|---|---|---|
| `differential` | `differential::corpus_agrees_across_rust_llvm_and_the_evaluator` (`crates/ignite/tests/differential.rs`) | every merge (`task gate`) and `task quality` |
| `static` | `quality::static_metrics_hold_the_bar` (`crates/ignite/tests/quality.rs`) | every merge and `task quality` |
| `conformance` | `quality::conformance_claims_hold_the_bar` | every merge and `task quality` |
| `perf` | `ignite-perf quality` (`tools/ignite-perf/src/quality.rs`), each value with the 1-minute load at its start | `task quality` only. The sizes (3.2, bytes) are deterministic and held against their bars like any count. The timing rows (ms: 5.3, 6.1, 6.2) are recorded as `host: local` and gate nothing, because timing on the shared workstation is not comparable between runs. Their bars are the first assessment's local values, kept as a reference. A later story (`story:quality-timing-host`) measures these rows on a single-tenant EC2 host (`host: ec2:<type>`); then they become gated. |

The per-merge tests refuse, as the UI ratchet (`ux/baseline.json`, `site::ux::ratchet`) does: a
value worse than its bar beyond the tolerance, a bar the run did not measure, a measured value
without a bar, an improvement not written into the baseline, and, against `main`'s baseline, a
bar made worse or a tolerance loosened without a `decision` on the bar.

## The differential runner

Metric 1.1 is the gate `story:mid-level-ir` lands behind. The runner takes every `.ignite` file
with inline tests or an executable under `crates/ignite/tests/fixtures/` (diagnostic fixtures,
those with an `.expected` file, left out), `examples/` (design files left out) and `std/`, that
checks. Each inline test runs as the test runner runs it (`--run-one`) on both targets and through
`Evaluator::run_test`; each executable runs without arguments on both targets, except a server
or a process starter (a system with a `TcpListener` or a `Launcher`), and the evaluator runs a
printer's main (a component of type `Printer`: the debug text of every fn without parameters).
Rust is the reference: LLVM agrees when exit status, stdout and stderr are equal, the evaluator
when it passes where Rust exits 0 or fails with the report Rust prints where Rust exits 101.

A difference fails the gate unless `known_differences` lists it with its consumer and the story
that fixes it (and a failing test committed `#[ignore = "story:<id>: …"]`); a listed difference
that is gone fails too. A difference that depends on the machine's load (a timing assertion) is
listed with `"intermittent": true`: it may show or not in a run, is not refused as gone and is
not counted in 1.1, which counts the steady differences. The units the evaluator cannot run are listed in `eval_cannot_run` with
the reason, exactly; their count is metric 1.6. Every outcome of a run is in
`target/quality/differential.json`.

## `task quality` and releases

`task quality` measures every instrumented metric once: the three per-merge tests, then
`ignite-perf quality`, then `quality::record`, which appends the run to `quality/history.jsonl`
with its host and regenerates `quality/trend.md`, the table below and the book page.
`IGNITE_BLESS=1 task quality` writes improvements of the count rows into the bars and gives a
timing row without a bar its first value. With `RUN=vX.Y.Z` the run is a release:
`quality::record` refuses it when a count row is worse than at the last release (or the bar,
before the first release) beyond its metric's tolerance, and then records the run as `run`, not as
the release. Timing rows are not part of the refusal yet; they join it once they are measured on
the dedicated host (`story:quality-timing-host`). The release steps in `AGENTS.md` § Releases
run it.

## Hill-climbing

The `target` column names the target of a metric where one is set. A wave that moves a metric
records the change in its close (the wave page under `.engineering/waves/` and the PR body): the
metric, the target, the value before and after, and the run of `task quality` that measured it.
