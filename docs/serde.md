# Data formats: one value model, derived codecs, JSON, YAML and TOML

**Status:** future design, not a slice contract. Nothing here is implemented.
**Date:** 8 November 2026
**Scope:** turning Ignite values into JSON, YAML and TOML text and back, without a hand-written
encoder and decoder per type. Called "serde" after the Rust crate; the mechanism differs (section 3).

Direction (Timo, 2026-11-08): a design for serde in Ignite, covering YAML, JSON, TOML and others.

This document decides. Each section states the chosen design and the alternatives it rejects.
References cite `docs/slice.md` as "slice §n", `docs/vision.md` as "vision", a file and line
otherwise.

## 1 The problem, measured

| where | what is written by hand today | size |
|---|---|---|
| `examples/todo/todo.ignite:59-70` | `to_json`, `to_record` for `Todo`, and their decoding | 3 functions |
| `std/protocol/jsonrpc.ignite:250-371` | `message_json`, `decode`, `decode_response`, `decode_body` | about 120 lines |
| `ignite-lsp/src/lsp_types.ignite` | generated by the tool `ignite-lsp-types`, checked in | 9,882 lines, 533 `to_json`/`from_json`/`encode_*`/`decode_*` functions |
| `examples/todo/health.ignite:132` | `encode_check`, one line of the model encoding | 1 function |
| pusher case study G9 (`docs/friction.md` row 68) | no YAML in std: rules written as Ignite data | |

Every one of these is mechanical: a record becomes an object of its fields, an enum a tag, an
option an absent member. The compiler knows every type's shape (`ignite emit --typed-json`,
slice §24 prints it), so it can write these functions.

## 2 Goals and non-goals

Goals:

1. `encode(todo)` and `decode(value)` for every data type, with no code per type.
2. JSON, YAML and TOML read and written by `std`, in Ignite, on both targets and in the
   compile-time evaluator.
3. Wire names that differ from field names (LSP's `languageId` for `language_id`) without
   attributes on fields.
4. Decode errors that name the path (`$.items[2].title`) and what was expected.
5. Bounded input: depth, size and entry limits, as `JsonRpcLimits` does.

Non-goals for the first version:

- Streaming (a decoder that never holds the whole document). Section 9.
- Binary formats (CBOR, MessagePack) and CSV. They fit the value model; section 9.
- Per-type hand-written codecs that replace the derived one. They need user `interface` and
  `impl` (section 3.2); section 9.
- YAML anchors, aliases and tags. Section 6.2.

## 3 The design in one page

```ignite
import std.data.{encode, decode, Shape, Case}
import std.yaml
import std.json

type Rule {
  name: Text
  match_path: Text
  rate_limit: Option<Int>
  action: Action
}

enum Action { Allow, Deny(Text), Redirect { to: Text, status: Int } }

fn load(text: Text) -> Result<List<Rule>, Text> {
  let value = yaml.parse(text).map_err(|e| e.message)?
  decode(value).map_err(|e| e.describe())
}

fn wire(rules: List<Rule>) -> Text =
  json.emit(encode_with(rules, Shape { keys = Case.Camel, ..Shape.default() }))
```

The block is a sketch: its syntax (closures, `..` record update, `yaml.parse` by module name) is not checked against the parser.

Three layers, each usable alone:

| layer | module | what |
|---|---|---|
| value model | `std.data` | `Value`, the tree every format reads into and writes from; `Shape`; `DecodeError`; `DataLimits` |
| codec | `std.data`, compiler-derived | `encode<T>(value: T) -> Value`, `decode<T>(value: Value) -> Result<T, DecodeError>`, `encode_with`, `decode_with` taking a `Shape` |
| formats | `std.json`, `std.yaml`, `std.toml` | `parse(text) -> Result<Value, FormatError>`, `emit(value) -> Result<Text, FormatError>` |

### 3.1 Why a value tree, not serde's visitors

Rust's serde never builds a tree: `Serialize` drives a `Serializer` and `Deserialize` is driven by
a `Deserializer`, through two traits and a visitor per type. That design needs user traits with
generic methods, and it exists to avoid allocation.

Ignite has neither prerequisite. User `interface` and `impl` are not in the language: a bound
naming anything but `ByteStream` is E099 (slice §18.7, vision row "user `interface` and `impl`",
P4). Ignite values are immutable values already, and every format here parses into a tree anyway
(`std.json.parse` returns `Json`). A tree costs one more allocation pass per document and buys:
each format is written once, against `Value`, not once per type; each type's codec is written
once, against `Value`, not once per format. N formats plus M types, not N times M.

Rejected: serde's visitor design (needs user interfaces with generic methods; P4 at the earliest).

### 3.2 Why the compiler derives the codec

| option | what it is | rejected because |
|---|---|---|
| A, chosen | the frontend writes `encode`/`decode` for each type a program uses, as ordinary typed functions | |
| B | a code generator per project, as `ignite-lsp-types` | a build step per project; 9,882 checked-in lines for one protocol |
| C | runtime reflection: type descriptors in the binary | the LLVM target carries no type information at run time; one more runtime ABI in `ignite-rt` |
| D | Rust serde crates in the substrate | the substrate does IO only; formats are Ignite in `std/` (`AGENTS.md`, rules of the layout) |
| E | `derives [Data]` on each type | the opt-in carries no information: a type is encodable exactly when its fields are |

Option A in detail:

- `encode` and `decode` are builtin generic functions of `std.data`, the way `Pipe.pair()` is a
  builtin of `std.net`.
- At each instantiation with a concrete `T`, `ignite-types` records `T`. After typing, one pass
  writes, for every recorded type and every type reachable from its fields, two typed functions
  (`encode` and `decode` of that type), shared by every instantiation.
- The written functions are ordinary typed items. Both backends and the evaluator compile them
  like any user function: no backend change and no runtime change. Once the mid-level IR
  (`story:mid-level-ir`) lands, the pass moves there.
- `ignite emit --typed-json` lists the written functions, so a test can read what the compiler
  wrote.
- Recursive types (`enum Tree { Leaf, Node(List<Tree>) }`) give recursive functions; the pass
  visits each type once.

## 4 The value model (`std.data`)

```ignite
enum Value {
  Null
  Bool(Bool)
  Int(Int)
  Decimal(Text)       // any number Int cannot hold, as its exact text (slice §19.20)
  Text(Text)
  Bytes(Bytes)
  Moment(Text)        // a date, time or date-time, as RFC 3339 text (TOML's datetimes)
  List(List<Value>)
  Map(List<(Text, Value)>)  // keys in document order; a duplicate key is a parse error
}
```

- Map keys are `Text`. A format with other key types (YAML's `1: a`) gives their canonical text.
- `Json` stays: `std.json` gains `to_value(Json) -> Value` and `from_value(Value) -> Json`.
  `Bytes` becomes base64 text, `Moment` its text. `std.protocol.jsonrpc` and ignite-lsp keep
  working unchanged. Whether `Json` later becomes a name for `Value` is open question O3.

## 5 The default mapping

| Ignite | `Value` | decode accepts |
|---|---|---|
| `Bool`, `Int`, `Text`, `Bytes` | `Bool`, `Int`, `Text`, `Bytes` | the same; `Bytes` also from base64 `Text` |
| `Duration` | `Text`, `500 ms` | the same text |
| record | `Map` of its fields, in declaration order | members in any order |
| `Option<T>` field | member left out when `None` | absent or `Null` gives `None` |
| `Option<T>` elsewhere | `Null` or the value | the same |
| `List<T>`, tuple | `List` | `List` of the right length for a tuple |
| `Map<K, V>` | `Map`; `K` written as text: `Text` as is, `Int` in decimal, a unit-variant enum by its name | the same; another key type is E1xx at check |
| enum, unit variant | `Text` of the variant name | the same |
| enum, payload variant | `Map` with one member, the variant name, holding the payload (a record payload as a `Map`, one positional payload as itself, several as a `List`) | the same |
| capability types (`TcpStream`, `Directory`, `Launcher`, …), functions | not data | `encode`/`decode` of a type that contains one is a check diagnostic naming the field path |

Unknown members: ignored by default, an error with `Shape.unknown = Unknown.Deny`.

### 5.1 `Shape`: names and tags without attributes

Ignite has no field attributes, and adding them is a language change bigger than this feature.
Wire names follow rules, so they are data passed at the call:

```ignite
type Shape {
  keys: Case                       // Same (default), Camel, Pascal, Kebab, ScreamingSnake
  variants: Case                   // Same (default), …
  tagging: Tagging                 // External (default), Internal(Text): the tag as a member of the payload map
  unknown: Unknown                 // Ignore (default), Deny
  renames: List<(Text, Text)>      // exceptions: ("Type.field", "wireName"), ("Type.Variant", "tag")
  limits: DataLimits
}
```

- `renames` entries are checked at compile time when the `Shape` is a constant: a name that is
  no field or variant of a type the call reaches is a diagnostic. A `Shape` built at run time is
  checked when `encode_with`/`decode_with` runs, with a `DecodeError`.
- LSP is `Case.Camel` plus renames for its reserved words; Kubernetes YAML is `Case.Camel`;
  Cargo-style TOML is `Case.Kebab`.

### 5.2 Decode errors

```ignite
type DecodeError { path: Text, expected: Text, found: Text }
```

`path` is a JSONPath-like location (`$.rules[3].action.Redirect.status`); `describe()` gives one
line. The first error ends decoding; collecting every error is open question O4.

## 6 Formats

Each format is one std module in Ignite: `parse(text: Text) -> Result<Value, FormatError>`,
`parse_with(text, limits)`, `emit(value: Value) -> Result<Text, FormatError>`.
`FormatError { message, line, column, offset }` uses the positions `ignite check --json` uses.
A format declares `conforms` against a catalogue in `std/rfc/` (slice §19.19 allows catalogues
named by a text `id`), so `ignite conformance` reports its coverage.

### 6.1 JSON (`std.json`, exists)

RFC 8259, unchanged parser. Adds `to_value`, `from_value`, `parse_value`, `emit` (compact) and
`emit_pretty`.

### 6.2 YAML (`std.yaml`, new)

YAML 1.2.2, core schema, a safe subset:

- Block and flow collections; plain, single-quoted, double-quoted, literal (`|`) and folded (`>`)
  scalars; comments; several documents in one stream (`parse_all`).
- Core schema only: `true`/`false`, `null`/`~`, decimal, octal `0o` and hex `0x` integers. `yes`,
  `no`, `on`, `off` stay text (YAML 1.1's boolean list is not read).
- Refused with a `FormatError` naming the line: anchors and aliases (exponential expansion),
  explicit tags except `!!binary`, complex (non-scalar) keys, the `<<` merge key.
- `emit` writes block style, two-space indent, and quotes any text a reader would take for
  another type (`"no"`, `"1.0"`, `"null"`).
- Tested against the YAML test suite (`yaml/yaml-test-suite`), vendored under `docs/yaml/` like
  `docs/rfc/`; cases using refused features are listed as expected refusals.

Pusher G9 needs this module first.

### 6.3 TOML (`std.toml`, new)

TOML 1.0.0, complete:

- Tables, inline tables, arrays of tables, dotted keys, all string forms, integers (`_`, `0x`,
  `0o`, `0b`), floats as `Decimal` text, `inf`/`nan` refused on decode into `Int`.
- Offset date-time, local date-time, local date, local time as `Moment`.
- The root of a document is a `Map`. `emit` refuses a root that is not a `Map` and a `Null`
  anywhere (TOML has no null); `None` fields are left out before that.
- Tested against `toml-lang/toml-test`, vendored.

## 7 Compile time

The evaluator runs the format modules and the derived functions like any pure Ignite (slice
§15). With a declared build input this gives configuration typed at check time:
`const SETTINGS: Settings = decode(toml.parse(input("settings.toml")))`, a diagnostic for a bad
file at `ignite check`. Declared build inputs do not exist yet (design §3.5); open question O2.

## 8 Delivery

| step | story (draft) | contents | needs |
|---|---|---|---|
| 1 | `data-value-model` | `std.data` `Value`, `Shape`, `DecodeError`, `DataLimits`; `std.json` bridge | |
| 2 | `data-derived-codec` | `encode`, `decode`, `encode_with`, `decode_with`: the frontend pass, both targets, evaluator, the not-data diagnostic, `typed-json` listing | 1 |

| 5 | `data-adopters` | todo's hand codecs replaced; ignite-lsp-types output measured against `Shape { keys = Camel }` | 2 |

Steps 2, 3 and 4 can run in one wave after step 1: they touch disjoint files (`crates/ignite-types`
and `std/data.ignite`; `std/yaml.ignite`; `std/toml.ignite`). Each step adds its rows to the
quality ratchet (`docs/quality.md`): round-trip tests per format and target, the differential
over the evaluator and both targets.

## 9 Later

- **Hand-written codecs** for one type (a `Duration` as seconds, a legacy wire form), once user
  `interface` and `impl` exist: `impl Data for T` replaces the derived pair for `T`.
- **Streaming**: `std.json.events(stream)` over a `ByteStream` for documents larger than memory.
- **Binary formats**: CBOR (RFC 8949) and MessagePack map onto `Value` directly, `Bytes` native.
- **CSV**: a `List` of records as rows, header from the field names.
